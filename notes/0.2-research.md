## 1. Protocol & relay strategy (outbox model, NIP-65, relay hints, ingestion)

What satori already has (do not re-recommend): outbox routing with set-cover and
per-shard targeted queries (`crates/core/src/pool.rs`, D33), seen-on + latency
sidecars (`crates/core/src/seen.rs`, `relay_latency.rs`), NIP-40/NIP-09
chokepoint filtering (D34), publish write-ahead queue + write-dead learning
(D36/D37, `outbox_queue.rs`), hourly follows-list refresher (D33).

Ideas from Dark Wisp that satori **lacks**:

1. **Relay hint store as a general fallback tier** — `repo/RelayHintStore.kt`
   accumulates per-pubkey relay hints from (a) p-tag/e-tag relay URLs at index 2
   (`extractHintsFromTags`, ~line 56) and (b) author provenance ("which relay
   delivered this event", `addAuthorRelay`, ~line 50), capped at 5 hints/pubkey,
   2000 persisted, LRU 5000. Satori's `seen.rs` records seen-on for *events*;
   it does not build a per-**author** relay index usable when an author has no
   kind 10002. The webapp had the same gap (`src/data/seen-relays.ts` is
   event-keyed). Actionable: key `seen.rs` lookups by author as a second index
   (sidecar, same D33 discipline) and feed it into `fetch_route`'s per-shard
   relay choice and `get_from`'s fallback chain.
2. **Redundancy-scored relay set (per-follow cover)** —
   `relay/RelayScoreBoard.kt`: for each followed author keep up to
   `MIN_REDUNDANCY = 3` of their write relays (`recompute()`, ~line 88), with
   recomputation gated on follow-set change (`needsRecompute()`), hint-derived
   authors kept in a separate map so confirmed 10002s overwrite them (~line 45).
   Satori's D33 shards authors across relays (≤2/author from pool.ts); the
   redundancy ≥3 rule is a stricter availability guarantee worth adopting for
   the follows feed specifically.
3. **REQ-size chunking to avoid silent relay rejection** —
   `relay/OutboxRouter.kt` (`MAX_AUTHORS_PER_FILTER = 200`,
   `MAX_ETAGS_PER_FILTER = 150`, ~lines 20–31): one sub-id, filters expanded
   per author-chunk, because big relays reject "total filter items too large"
   *silently*. Satori's `fetch_route` builds multi-author shards; verify
   (and if needed enforce) chunk ceilings there.
4. **Top-N instead of broadcast for metadata-style fetches** —
   `sendChunkedToTopRelays(maxRelays = 10)` (~line 60) and
   `sendToRelayOrEphemeral` for indexer work (`repo/PeerRelayListLookup.kt`).
   Satori already routes shards, but kind-0 hydration and own-kind
   backfill still fan wide in `manager.rs`; a "top-N by learned latency"
   cap is a cheap win on top of `relay_latency.rs`.
5. **Relay health sessions with 5xx-only bad-marking** —
   `relay/RelayHealthTracker.kt`: connect→disconnect sessions with
   events-received counts (`MAX_SESSION_HISTORY = 10`,
   `MIN_SESSION_DURATION_MS = 30s`), and "relays are marked bad only when they
   return a 5xx HTTP error — rate limiting and mid-session disconnects are not
   penalised" (class doc). Satori's `relay_latency.rs` has EWMA + read-dead +
   write-dead (D36) but no session-level lifetime stats; the per-account
   "RelayHealth" surface (`ui/screen/RelayHealthScreen.kt`) is also a nice
   settings pane satori's relay pane lacks (webapp had NIP-11 browse,
   `src/data/relay-info.ts`; desktop settings.rs has no NIP-11 surface — grep
   confirmed).
6. **Bounded signature-verification pipeline** —
   `relay/BoundedVerification.kt`: key-hash single-flight per payload, 4
   workers, bounded queue (admission suspends rather than skipping), per-worker
   LRU result cache (256), fail-closed on any throwable. Satori verifies
   everything client-side (§1.1) via nostr-sdk; if verification ever shows up
   in profiles, this is the shape to copy (satori's equivalent gate is the
   pool chokepoint `consume_and_filter`, pool.rs — currently synchronous).
7. **Onboarding relay prober** — `relay/RelayProber.kt`: harvest kind:10002s
   (`HARVEST_LIMIT = 500`), tally frequencies, drop mega-relays
   (`TOP_EXCLUDE = 5`), probe 15 candidates at 8s timeout, keep
   `TARGET_COUNT = 8`. A first-login "pick good relays for me" flow is
   entirely absent from satori (login.rs is bunker-only) and fits the
   cypherpunk default of user-chosen relays.
8. **DM inbox-relay lookup with cache + timeout** — `repo/DmRelayLookup.kt`
   (kind 10050, indexer set, 4s window, LRU via DmRepository) and
   `OutboxRouter.publishToInboxes` (~line 332: own write relays ∪ union of
   targets' inbox relays, deduped). Directly relevant when M3 (NIP-17 DMs,
   postponed §10) is re-prioritized — satori's `dms.rs` exists but no relay
   management UI shipped.
9. **Persisted metadata cache with write-behind batcher** —
   `repo/PersistedMetadataCache.kt` (LRU 2000, dirty-map + `db/BatchWriter.kt`
   settle 200ms / max-batch 500, failure reported exactly once). Satori's
   profile map lives in memory (`manager.rs`) with LMDB events; a generic
   bounded write-behind sidecar utility would harden the D33 sidecar family
   (currently each has a hand-rolled flusher).
10. **Spam scoring on ingest (optional, heavy)** — `ml/NSpamClassifier.kt`
    (LightGBM over note features, capped 10 newest notes). Satori's filter
    model is user keyword/regex (M3 row, §7). Note only; ML is likely against
    the uncarved-block principle — record as considered-and-doubtful.

## 2. Performance (caching, windowing, startup, memory)

Satori already did the big ones: bounded decoded-image LRU + gpui asset
co-eviction (D14), feed windowing 1000→400 with off-window paging anchor
(D24), decode-header bomb check + concurrency gate (D22/D24), LMDB
cold-start paint (D14), mimalloc (D33 note).

Ideas from Dark Wisp not yet in satori:

1. **Viewport-scoped engagement/engagement-subscription state** —
   `viewmodel/FeedEngagementState.kt`: track which event ids have live
   engagement subscriptions and drop "distant" ones
   (`distantSubscriptions(nearbyIds)`, plus a `viewportRange(feedIds,
   visibleIds, before, after)` helper) — i.e. per-note engagement REQs are
   subscribed only near the viewport. Satori's engagement set
   (`engagement.rs`) is loaded per paint from store; there is no live
   engagement subscription pooling at all. A desktop analogue: batch
   engagement REQs for visible-window ids, drop on scroll-away.
2. **Batched DB writes** — `db/BatchWriter.kt` (settle 200ms, batch 500,
   unbounded channel, fail-once reporting). Satori's LMDB writes go through
   nostr-sdk per event; if ingest CPU ever profiles hot, a coalescing writer
   in front of the store is the pattern.
3. **Bounded TTL caches as a reusable primitive** —
   `repo/BoundedExpiryCache.kt` (insertion-ordered, TTL + capacity,
   snapshot-for-persistence). Cleaner than ad-hoc maps for things like the
   `deletions::should_check` 30-min TTL gate (D34) and NIP-05 verdicts.
4. **Collector-owned observation channels** — `repo/KeyedObservation.kt`:
   obtaining a Flow allocates nothing; collectors register conflation channels
   torn down on drop. A GPUI analogue (per-entity subscription registry that
   self-cleans when the entity releases) would prevent the classic
   notify-everything storm noted in D14 ("`cx.notify()` fires for every
   profile resolution").
5. **Network-change awareness** — `relay/ConnectivityFlow.kt`: react to
   transport changes with debounce; on a desktop this maps to
   NetworkManager/nm signal or simply reconnect-on-wake: satori currently
   relies on SDK keepalive (D14 accepts ~6% idle CPU; a suspend/resume
   reconnect sweep is unverified and worth a soak test).
6. **Search debounce tiers** — `viewmodel/SearchViewModel.kt` uses staged
   delays (500ms store pass, 3s relay pass, 5s deep pass at lines
   135/207/331). Satori's search.rs is a single NIP-50 query; staged
   "instant store results → relay fill" would feel faster.

## 3. UI/UX gaps vs the webapp (each confirmed missing in crates/)

1. **Scheduled posts** — webapp: `src/data/scheduled.ts` (signed-at-compose,
   disk-held, broadcast by a 30s sweep, `GIVE_UP_SECS = 3600`, restart-safe,
   mtime-cached reads); §7 row "scheduled posts (restart-safe sweep)" and §3.3
   `scheduled.json`. Desktop: `crates/core/src/config.rs:21` reserves
   `SCHEDULED: scheduled.json`, but grep finds **no sweep, no type, no UI**
   anywhere in `crates/core/src/manager.rs`, `session.rs`, or
   `app-gpui/src/views/composer.rs`. This was an M5 item that silently never
   landed — and unlike Tor items it has no dependency: the outbox queue
   (D36) already gives the write path. Cheapest "lost feature" to restore.
2. **Composer: emoji typeahead and `:shortcode:` completion** — webapp §7 row
   "@mention/`:emoji` typeahead" (src/render/compose.ts). Desktop composer.rs
   has @-mention detection (`detect_mention`, composer.rs:227) but **no
   emoji-shortcode typeahead** (grep: no `typeahead` hits). Emoji sets were a
   webapp data file (`src/data/emoji-sets.ts`); desktop has no custom-emoji
   (NIP-30) picker surface even though `nip/` covers NIP-30 tags.
3. **Relay favorites / relay sets (NIP-51 `relay` sets) UI** — webapp:
   `src/data/relay-favorites.ts`. Desktop settings.rs has relay panes per §7
   but no favorites/sets (grep of settings.rs for nip11/latency surfaces: no
   hits beyond basic panes). Low priority, but the webapp's relay **latency
   display** (`src/data/relay-latency.ts`) is half-ported: the data exists in
   `relay_latency.rs` (D33) and is invisible — surfacing per-relay
   latency/read-dead state in the settings relay pane is a near-free polish
   win.
4. **Undo-window countdown pill in the feed** — webapp: `src/undo.ts`
   (signed event held server-side; countdown pill polls `/note/tick`;
   backstop auto-commit). Desktop: `crates/core/src/undo.rs` ports the hold +
   backstop, and the composer shows it — confirm the *post-publish* pending
   state (outbox queue item visible as "delivering…" with retry count) is
   surfaced anywhere; D36 only logs later successes ("a later outbox success
   is logged, not re-toasted"). A quiet "1 note queued for delivery" state in
   the shell rail would close the honesty gap D36 opened.
5. **Keyboard UX** — the GTK port had "/" opens search and escape-to-back
   (TODO(port) citations to `crates/app/src/main.rs`); the GPUI shell binds
   **no global keys** (grep: only composer.rs:28 `ctrl-enter` and the
   Input-context editor keys in `crates/app-gpui/src/input.rs`; shell.rs:6
   comment: "gpui actions land with the composer in P2, when there are more
   keys to bind"). Desktop-appropriate set: `/` search, `Esc` back/lightbox,
   `j/k` feed, `n` compose, `g h` home. Pure GPUI `bind_keys` work, no core
   changes.
6. **Zero-JS affordances that never re-landed as native equivalents** — the
   webapp had `h-prefetch="hover"` on all rail links
   (`src/render/layout.ts:118–177`) i.e. hover-prefetch of profile/search
   pages. Native analogue: warm the profile feed (kick `profile_older` +
   kind-0 fetch) on rail hover 200ms. Cheap and invisible.
7. **Notification bell dot semantics** — webapp layout.ts:79 (`notif-dot`,
   90s poll, re-arm discipline at layout.ts:72–76). Desktop notifications view
   exists (`views/notifications.rs`, D18 stream), but there is **no shell-rail
   unread dot** (grep of shell.rs: no bell/dot). The bell poll and read-state
   machinery (`read_state.rs`) exist core-side; only the rail indicator is
   missing.
8. **Quote/reply "in reply to an earlier note" lazy parent hydration** —
   webapp: `src/render/note.ts:216–219` (`h-trigger="intersect once"` →
   `/embed/<bech>?as=reply`). Desktop thread.rs hydrates mentioned pubkeys
   (thread.rs:89 TODO(port)) and quotes render as cards, but the *missing
   parent* case ("↩ in reply to an earlier note" + lazy fetch by bech hint)
   is not ported — grep finds no equivalent in cards.rs/thread.rs.
9. **Media: gallery card / full-screen pager** — webapp `src/routes/media.ts`
   + image-proxy routes; desktop has profile media strips + lightbox
   (profile.rs) and D32 poster ladder, but no multi-image **carousel inside a
   note card** (Dark Wisp `ui/component/MediaCarousel.kt`,
   `FullScreenMediaPager.kt` — see §4). NIP-68 multi-imeta notes degrade to
   first image only in cards.rs (verify — `imeta` list handling exists in
   core but cards show one).

## 4. UI/UX ideas from Dark Wisp (with file citations)

1. **MediaCarousel + FullScreenMediaPager** (`ui/component/MediaCarousel.kt`,
   `ui/component/FullScreenMediaPager.kt`): multi-imeta notes render a swipeable
   carousel with position dots; full-screen pager shares decode state. Satori's
   sumi-e idiom: a row of thumbnails or a "1/3" counter on the card, lightbox
   arrows through the set (lightbox already exists per profile.rs:38).
2. **AltTextBadge + AltTextEditorDialog** (`ui/component/AltTextBadge.kt`,
   `AltTextEditorDialog.kt`): alt-text presence badge on media and an editor at
   compose time. Satori posts pictures (NIP-68) with no alt-text surface at all
   (composer.rs grep: none). Accessibility + cypherpunk-honesty fit; pairs with
   the M5 a11y pass.
3. **ThreadFlattener with connector lines** (`viewmodel/thread/ThreadFlattener.kt`,
   `ui/component/ThreadIndent.kt`, `CollapsedRepliesRow.kt`): flatten deep trees
   to a linear list with indent glyphs and a "N collapsed replies" expander row.
   Satori threads at depth 4 with private replies folded (§7); the collapsed-row
   affordance for wide subtrees is a concrete upgrade to thread.rs.
4. **NsecPasteGuard** (`ui/component/NsecPasteGuard.kt`): detects pasted private
   keys anywhere in the app and warns/intercepts ("you just pasted an nsec into a
   non-login field"). Given D17's key-hostility stance, a shell-level clipboard
   nsec tripwire is very on-brand and ~50 lines.
5. **RelayIcon inline glyphs** (`ui/component/RelayIcon.kt`): per-relay favicon
   rendered inline on note cards ("via nos.lol"). Quiet provenance signal; fits
   the dots-not-badges rule if done as a hover-only detail on the timestamp.
6. **EmojiShortcodePopup / EmojiPicker** (`ui/component/EmojiShortcodePopup.kt`,
   `EmojiPicker.kt`): `:`-triggered shortcode completion with a palette — the
   concrete interaction model for gap §3.2 above.
7. **Haptics → desktop equivalents**: `ui/component/HapticHelper.kt` maps to
   subtle motion (already the D23 discipline). Skip.
8. **Staged search** (`viewmodel/SearchViewModel.kt:135–331`): see §2.6.
9. **ConsoleScreen** (`ui/screen/ConsoleScreen.kt` + `relay/ConsoleLog.kt`): an
   in-app relay/event log surface. Satori has `diag.rs` (debug metrics, §7
   Sovereignty row) but no viewer; a hidden "console" pane in settings would
   make field-debugging (like D36's publish postmortem) self-serve.
10. **KeepScreenOn / PipController** — mobile-only, skip. **ZoomableAsyncImage**
    (`ui/component/ZoomableAsyncImage.kt`): pinch-zoom; desktop analogue is
    click-drag pan + scroll-zoom in the lightbox — check lightbox supports zoom
    (profile.rs lightbox is nav-only per line 38 context).

## 5. Recommended 0.2 scope — ranked shortlist

Already ruled out / deferred (do not propose): YouTube in-app embed (§10,
external browser for v1), multi-account (D10), arti in-process (§10), engine.ts
wire-manifest (§10), M3 DMs (§10 — postponed; the DmRelayLookup item waits).

### Quick wins (days, no structural risk)

1. **Global keyboard bindings** — `/`, `Esc`, `j/k`, `n` via `bind_keys` in
   shell.rs (§3.5). Pure app-gpui.
2. **Scheduled posts** — the reserved `SCHEDULED` config (config.rs:21) +
   outbox queue (D36) make this small: sign-at-compose, `scheduled.json`
   sidecar, 30s sweep in manager.rs, composer field. Restores a §7-guaranteed
   feature (§3.1).
3. **Relay latency/health surfaced in settings** — `relay_latency.rs` data
   (D33) + write-dead state (D36) rendered as a passive pane; optionally the
   5xx-only bad-marking semantics from `RelayHealthTracker.kt` (§1.5).
4. **Shell-rail unread dot** for notifications (§3.7) — read_state.rs +
   notifications.rs already compute the stream.
5. **Composer emoji-shortcode typeahead** (§3.2 / §4.6) — local NIP-30
   shortcode table + the existing `detect_mention` trigger pattern.
6. **Nsec paste tripwire** (§4.4) — tiny, on-brand.
7. **Author-keyed relay hints** — extend `seen.rs` with a per-author index
   feeding `fetch_route`/`get_from` fallbacks (§1.1); sidecar discipline
   already exists.

### Structural work (weeks, decide deliberately)

8. **Relay scoreboard with redundancy ≥3 for the follows feed**
   (§1.2, `RelayScoreBoard.kt`) — changes feed REQ topology; measure against
   D33's shard routing first.
9. **Viewport-scoped live engagement subscriptions** (§2.1,
   `FeedEngagementState.kt`) — new subscription lifecycle in the manager;
   biggest feed-liveness upgrade since live mode, needs D24-window integration.
10. **REQ chunk ceilings + top-N metadata fetches** (§1.3/1.4,
    `OutboxRouter.kt`) — touch `pool.rs` `fetch_route`; needs relay-rejection
    reproduction to justify.
11. **Relay prober onboarding** (§1.7, `RelayProber.kt`) — a new first-login
    flow; product-shape decision (does it fit bunker-first? yes, but it's a
    new screen).
12. **Multi-image carousel in note cards + alt-text editor** (§4.1/4.2) —
    cards.rs + composer.rs + media.rs work; pairs well with M5 a11y pass.
13. **In-app console pane** (§4.9) — diag.rs viewer; do when next publish/relay
    incident demands it.

### Suggested 0.2 theme

"Quiet competence": items 1–7 (keyboard, scheduled, relay visibility, dot,
typeahead, nsec guard, author hints) are all polish-grade and use machinery
that already exists; items 8–9 are the only ones worth a design pass, and 9
(viewport-scoped engagement) is the single highest-leverage feed-feel upgrade
observed in either source.
